Migrating

From Radix

Radix parts to Kitora's primitives: names, render instead of asChild, the data attributes.

@kitora/primitives is Kitora's unstyled layer, the parts every styled component is built on. A Radix component maps onto it part for part: most names stay, a few are renamed, asChild becomes render, and the state attributes change spelling.

Before and after

Both examples are a controlled tab list and a controlled dialog, with a status line that shows what the callbacks reported.

Before

Name, icon and visibility.

Tab: general, dialog closed

After

Name, icon and visibility.

Tab: general, dialog closed

The two behave the same: Tab reaches the selected tab, the arrow keys (wrapping at the ends), Home and End move and select, a click selects, and the next Tab goes into the panel; the dialog opens by mouse or Enter, moves focus inside and keeps it there, and closes on Escape or its Close part with focus back on the trigger. The status line follows every change. The page's test drives both with the same clicks and keys and compares what a person and a screen reader meet after every step.

Part names

RadixKitora
Dialog.Root, Trigger, Portal, Title, Description, Closethe same names
Dialog.OverlayDialog.Backdrop
Dialog.ContentDialog.Popup
Tabs.Root, Tabs.Listthe same names
Tabs.TriggerTabs.Tab
Tabs.ContentTabs.Panel

Radix also exports each part under a long name (DialogContent for Dialog.Content, Tabs for Tabs.Root), which the Before uses. Dialog and Tabs list every Kitora part and prop.

Props

  • asChild becomes render. Instead of passing your element as the only child, pass it to render; the part draws that element with its own props and behaviour merged in, and the part's children go inside it.
  • The controlled props keep their names. open with onOpenChange, value with onValueChange. Each callback gets the new value first, as in Radix, and the event details second: a reason and cancel(), which refuses the change. A tab's value can be of any type, so the After turns it into a string.
  • Activation. A Radix tab list selects a tab as the arrow keys reach it (activationMode="automatic", its default). Kitora's list moves focus only and selects on Enter or Space unless you set activateOnFocus, which the After does to keep Radix's behaviour.
  • Keeping content mounted. Radix's forceMount is keepMounted: on Dialog.Portal it keeps a closed dialog in the page, hidden; on Tabs.Panel it keeps an unselected panel, hidden.

State attributes

Radix writes one data-state attribute; Kitora writes one attribute per state, so a class written for Radix needs the new name:

RadixKitora
data-state="open"data-open
data-state="closed"data-closed
data-state="active" on a tabdata-active
data-state="inactive" on a tabno data-active
data-orientationthe same

In Tailwind, data-[state=open]: becomes data-open: and data-[state=active]: becomes data-active:, as in the two examples' class strings.

Two differences you will not see

  • Behind an open dialog, Radix hides the rest of the page from screen readers with aria-hidden; Kitora makes it inert, which also keeps clicks and focus out of it.
  • The tab stop. Radix makes the tab list itself the stop and passes focus on to the selected tab; Kitora makes the selected tab the stop. Either way one Tab press lands on the selected tab.

The page's test sets aside these two and the attribute spellings above, plus ARIA defaults that one side writes out and the other leaves out (such as aria-orientation="horizontal" on the tab list) and elements no screen reader reaches (an unselected panel, the backdrop); its comparison file lists each one. Everything else, roles, names, the rest of ARIA and focus, is compared as it is. The primitives contract explains the names and attributes every primitive shares, and Build your own component builds a dialog from these parts. If your app is on shadcn/ui rather than plain Radix, see From shadcn/ui.
