Theming and your own design language

Brand tokens, then a design language of your own with its slots.

Theming has two steps. First put your brand into the design tokens, the CSS variables every component reads. Then, if colours are not enough, write a design language of your own that also changes how components are shaped. Everything here comes from @kitora/theme.

Brand tokens

buildTheme takes your brand colour, a base radius and a density, and returns the full set of tokens for light and dark. It fits the text colours to the contrast you ask for (contrast, WCAG AA by default), so text on your brand colour stays readable. toCss writes the tokens as plain CSS variables, light on :root and dark on .dark; toTailwindV4 writes the same with the Tailwind theme block, for the CSS file your build reads (the install page shows it), plus the rest of Kitora's default look: the Geist font stacks (load Geist itself, for example @fontsource-variable/geist), tracking, the shadow scale, status and chart colours, motion tokens and the base rules. With no options, toTailwindV4(buildTheme()) is exactly this site's theme. The sidebar's colours (--sidebar, --sidebar-foreground, --sidebar-border and the rest of the shadcn sidebar-* names) are theme tokens like the others, derived from the theme's own surfaces, so @kitora/sidebar follows your brand and neutrals in light and dark; buildTheme's overrides set one directly.

ThemeScope applies a theme to one subtree, which is handy for a preview. In an app you write the stylesheet once and need no component at all. The theme designer picks the brand, radius and density with controls and exports the result.

Light and dark

ThemeProvider owns the colour mode (light, dark or system), the density, and optionally a generated theme. ModeToggle and DensityToggle from @kitora/theme/ui read and write the nearest provider. Leave the choices uncontrolled and the provider remembers them in its storage (localStorage unless you pass another); pass mode and density to control them yourself.

Light, dark and density

At an app's root the provider writes to <html>; the providers page shows where it goes, and the server rendering page shows the boot script that keeps a saved choice from flashing.

A design language of your own

A design language restyles components, not only colours: corners, heights, fills, focus rings and more, one slot per component (see Design languages). A language is plain data, so make yours by copying a built-in and changing the slots you care about. Its tokens can keep the page's own (source: "host") or be generated from a brand colour (source: "generated"), as below.

Define, register and switch to a language

New

validateLanguage: no problems

  • Register it on a registry that already holds the built-ins (builtinLanguageRegistry()), then pass the registry to the provider's languages prop. A provider reads its registry once, so register first.
  • Validate it with validateLanguage: it returns every problem as a path and a message (slots.button.heights.md: expected a positive number), and an empty list when the language is valid. register runs the same check and throws with every problem listed.
  • Switch to it like any built-in, with setLanguage(id) from useLanguage(). The provider sets data-language, and the language's slot variables (--dk-button-radius and the rest) follow.
  • Load saved JSON (an import, a save from an older release) with tryCompleteLanguage: it fills the slots the JSON lacks from Kitora before it checks.

You do not have to write the data by hand. The customizer builds a language with controls drawn from the slot schema, saves it in the browser and exports it as JSON. The languages page shows every built-in side by side, and the theme guide shows how to make a component of your own read a slot.
