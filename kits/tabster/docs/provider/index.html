Provider & composition

Tabster works as a single component. For richer UIs — adding a layout outliner sidebar, an arrange-mode overlay, or per-group label chips — several pieces need to share the same imperative api, names registry, and DOM host. <TabsterProvider> owns that shared state so siblings read it from context instead of receiving props from you.

Shape

<TabsterProvider>
  <TabsterDockHost>
    <Tabster panels={PANELS.panels} initialPanels={INITIAL} />
    <TabsterArrangeOverlay active={arrangeMode} />
  </TabsterDockHost>
  <TabsterOutliner
    panelCatalog={PANEL_CATALOG}
    mode={outlinerMode}
    onModeChange={setOutlinerMode}
  />
</TabsterProvider>

That's it — no api={} / hostRef={} / namesStore={} props.

Wiring details

  • <TabsterProvider> creates a fresh TabsterGroupNamesStore on mount.
  • <TabsterDockHost> renders a relative min-w-0 flex-1 div with a ref registered on the provider — the arrange overlay positions tiles relative to it.
  • <Tabster> reads the context and:
    • auto-publishes its imperative api on onReady
    • auto-binds a createTabsterGroupLabel(store) if you didn't pass a groupHeaderPrefix explicitly
  • <TabsterOutliner> + <TabsterArrangeOverlay> fall back to the context for api, namesStore, and hostRef — explicit props still override.

Why not always require the provider?

You don't need outliner / arrange / label chips to use Tabster. The provider is opt-in. Standalone callers skip it entirely:

<Tabster panels={...} initialPanels={...} />

Sharing a names store across routes

If you want group names to survive route changes, hoist the store and inject it into the provider:

import { createGroupNamesStore } from '@kitora/tabster'

const sharedStore = createGroupNamesStore({
  defaultName: (n) => `Editor ${n}`,
})

function App() {
  return (
    <TabsterProvider namesStore={sharedStore}>
      <Routes />
    </TabsterProvider>
  )
}

Reading the same store from a child:

import { useTabsterContext } from '@kitora/tabster'

function GroupNameDebugger() {
  const { namesStore } = useTabsterContext()
  // …
}

useTabsterContext() throws when used outside a provider — pair with useOptionalTabsterContext() for shared components that should work both inside and outside.

Custom group-naming pattern

<TabsterProvider
  namesStoreOptions={{
    defaultName: (n) => `Workspace ${n}`,
    initial: { 'group-1': 'Inbox' },     // seed values
  }}
>
  …
</TabsterProvider>

The seeded entries survive reconcile — they don't get overwritten by the default pattern.

Standalone usage (no provider)

Every consumer still accepts explicit props as overrides. The earlier "manual wiring" pattern continues to work:

const apiRef = useRef<TabsterApi | null>(null)
const namesStore = useMemo(() => createGroupNamesStore(), [])
const hostRef = useRef<HTMLDivElement | null>(null)
const GroupLabel = useMemo(() => createTabsterGroupLabel(namesStore), [namesStore])

<div ref={hostRef} className="relative">
  <Tabster
    panels={PANELS.panels}
    onReady={({ api }) => (apiRef.current = api)}
    groupHeaderPrefix={GroupLabel}
  />
  <TabsterArrangeOverlay
    active={arrangeMode}
    api={apiRef.current}
    hostRef={hostRef}
    namesStore={namesStore}
  />
</div>
<TabsterOutliner
  api={apiRef.current}
  namesStore={namesStore}
  panelCatalog={PANEL_CATALOG}
  mode={outlinerMode}
  onModeChange={setOutlinerMode}
/>

Use the provider when you have ≥ 2 siblings reading the same wiring. For one-off Tabster mounts, skip it.
