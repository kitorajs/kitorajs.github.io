Datagrid — getting started

A power-user datagrid built on the same adapter pattern as the task list and Tabster. The grid never owns data — it asks an adapter for a page of rows, given the current search / filters / sort / pagination state. Swap the adapter, plug it into any backend.

Mental model

Three layers:

  1. Adapter — implements DataGridAdapter<TRow>. Mandatory: load(query). Optional: updateRow, deleteRow, bulkDelete, bulkUpdate, moveRow, bulkMoveRows, subscribe. The grid hides affordances for any mutator you don't supply.
  2. Providers — <DataGridUIProvider> holds UI state (search, filters, sort, pagination, selection, columns, density, layout); <DataGridProvider> runs the adapter and exposes rows + capabilities. Both required; clean separation of data vs UI.
  3. Plug-in feature components — <DataGridSearch>, <DataGridSort>, <DataGridFilterBar>, <DataGridPagination>, <DataGridColumnVisibility>, <DataGridDensityToggle>, <DataGridBulkActions>, <DataGridSelectionIndicator>, plus the core <DataGrid> (or <DataGridView> for multi-layout).

30-second example

import { useMemo } from 'react'
import {
  DataGrid,
  DataGridProvider,
  DataGridUIProvider,
  DataGridFilterBar,
  DataGridPagination,
  DataGridBulkActions,
  createInMemoryAdapter,
  defineColumns,
  defineSortOptions,
} from '@kitora/datagrid'

interface User { id: string; name: string; email: string; team: string }

const sortOptions = defineSortOptions()([
  { fieldId: 'name', label: 'Name' },
  { fieldId: 'team', label: 'Team' },
])

const columns = defineColumns<User>()([
  { id: 'name',  header: 'Name',  cell: (r) => r.name,  meta: { sortFieldId: 'name' } },
  { id: 'email', header: 'Email', cell: (r) => r.email },
  { id: 'team',  header: 'Team',  cell: (r) => r.team,  meta: { sortFieldId: 'team' } },
])

export function UsersPage({ initial }: { initial: User[] }) {
  const adapter = useMemo(
    () => createInMemoryAdapter({ initial, sortOptions, searchKeys: ['name', 'email', 'team'] }),
    [initial],
  )
  return (
    <DataGridUIProvider defaultPageSize={20}>
      <DataGridProvider adapter={adapter}>
        <DataGridFilterBar />
        <DataGrid columns={columns} />
        <DataGridPagination />
        <DataGridBulkActions />
      </DataGridProvider>
    </DataGridUIProvider>
  )
}

Why this kit — swap any layer, the rest still works

The whole point of the architecture is that every layer is replaceable in isolation. Use the defaults to ship in a day; swap any piece when your needs grow. The data layer, the pagination strategy, the renderer, and every individual UI primitive are independently pluggable.

1. Data — any backend

Adapter is one interface. Same UI, completely different data sources:

<DataGridProvider adapter={createInMemoryAdapter({ initial })} />  {/* prototype */}
<DataGridProvider adapter={myRestAdapter} />                       {/* prod REST */}
<DataGridProvider adapter={myGraphQLAdapter} />                    {/* prod GraphQL */}
<DataGridProvider adapter={myPrismaAdapter} />                     {/* SSR direct */}

Nothing else in the tree changes. Selection, filters, sort, search, shortcuts — all keep working.

2. Pagination strategy — one prop

<DataGridProvider adapter={a} />                            {/* paged (default) */}
<DataGridProvider adapter={a} paginationMode="infinite" />  {/* infinite scroll */}

Want to A/B paged vs infinite? Flip the prop. The features layer doesn't know which mode you picked.

3. Renderer — same data, different shape

The same provider drives every renderer. Pick what suits the data:

<DataGrid columns={cols} />                              {/* classic table */}
<DataGridVirtual columns={cols} />                       {/* windowed table */}
<DataGridView layouts={[cardsLayout()]} />               {/* card grid */}
<DataGridView layouts={[kanbanLayout()]} />              {/* kanban board */}
<DataGridView layouts={[mediaGridLayout()]} />           {/* gallery */}
<DataGridView layouts={[mediaGridLayout(), cardsLayout(), kanbanLayout()]} /> {/* user-picked */}

Selection, filters, sort, infinite scroll all carry across — switch renderers without losing state.

4. Slot overrides — every primitive is replaceable

Each layout takes custom React components for every visual piece:

mediaGridLayout({
  Card: MyCustomCard,         {/* reskin the whole card */}
  Thumb: MyCustomThumb,        {/* swap the thumbnail */}
  Checkbox: MyCustomCheckbox,  {/* swap the select chip */}
  ActionOverlay: MyOverlay,    {/* swap the hover actions */}
  Meta: MyMeta,                {/* swap the title / subtitle row */}
})

The interaction layer (hover, multi-select, rubber-band, drag-reorder, keyboard nav) stays intact while you reshape the look completely.

Drag handles are pluggable the same way — pick dragHandle: 'whole-card' | 'icon' | 'none' on the layout, OR place <DataGridRowDragHandle rowId> (with optional asChild) anywhere inside a cell renderer to turn any element into a drag handle. Multiple handles per row, custom buttons as handles — see the Row reorder doc.

5. Headless hooks — skip the components entirely

For fully bespoke UI, read state directly and render whatever you want:

const { rows, infinite } = useDataGrid()              // raw row data + load-more
const { selectedIds, toggle } = useDataGridUI()        // selection + UI state
useDataGridInfiniteScrollSentinel({ ... })             // your own load-more UI
useDataGridSelectMode(count)                            // your own select chrome
useDataGridRubberBand({ ... })                          // your own marquee
useDataGridLongPress({ ... })                           // your own touch handler
useDataGridSelectionShortcuts({ ... })                  // your own ⌘A / Esc

Build a gallery from scratch in 50 lines — <DataGridInfiniteAnchor> still fires, <DataGridBulkActions> still works, <DataGridFilterBar> still applies. The kit doesn't lock you into its components.

Why this works

The data layer (<DataGridProvider>) and UI-state layer (<DataGridUIProvider>) sit above every renderer. The renderer reads from both; the primitives read from both; your custom code reads from both. Nothing renderer-specific leaks upward, so:

  • Same selection model across table → cards → media-grid
  • Same filters / sort / search across every layout
  • Same infinite scroll across every layout
  • Same shortcuts (⌘A, Esc, ⌘-click, shift-range) across every layout

You can mix kit primitives with hand-rolled UI freely — the contract is the providers, not the components.

Adapter capabilities

Implement only what you need. The grid inspects the adapter via inspectCapabilities(adapter) and conditionally renders:

Adapter methodWhat appears
load(required) — rows, pagination, search-as-where, filter pills
updateRowInline edit on cells with meta.edit
deleteRowRow context-menu "Delete" item
bulkDeleteBulk Delete button in <DataGridBulkActions>
bulkUpdate"Edit selected (N)" in column-header menu
moveRowSingle-row drag-reorder
bulkMoveRowsMulti-row drag-reorder (drag your whole selection)
duplicateRowRow context-menu "Duplicate" item
subscribeRealtime updates pushed via onUpsert / onRemove

You ship a baseline load-only adapter, then add mutators as your backend grows. Each new method lights up its UI; nothing else changes.

Where to go from here

  • Adapter contract — full surface + REST/GraphQL recipe + in-memory reference impl.
  • Columns — cell renderers, pinning, inline-edit, drag-resize, aggregations, group-by.
  • Filters — filter fields, the filter picker, operators, buildWhere engine.
  • Selection — checkboxes, shift-click range, ⌘-click, rubber-band, long-press, ⌘A / Esc, indicator chip.
  • Row reorder — whole-row vs handle modes, <DataGridRowDragHandle>, place handles anywhere, two hook flavors.
  • Layouts — table / cards / kanban / media-grid + custom layouts via DataGridLayout.
  • MediaGrid — gallery view for asset libraries.
  • Features — live matrix of every feature, status, and shortcut.
