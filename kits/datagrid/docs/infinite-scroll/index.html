Infinite scroll

Looking for the big picture? This is the deep-dive on infinite specifically. For the overview of all three modes (paged / infinite / numbered), the unified hook, and every UI primitive, start at the Pagination doc instead.

Flip the data-layer provider to paginationMode="infinite" and mount one (or two) <DataGridInfiniteAnchor> sentinels. Cursor pages append (or prepend) into the same rows array that drives every layout. Selection, filters, sort, search, shortcuts, bulk actions — everything keeps working because nothing else in the kit knows about pagination mode.

30-second mount

<DataGridUIProvider defaultPageSize={30}>
  <DataGridProvider adapter={adapter} paginationMode="infinite">
    <DataGridFilterBar />

    <DataGridInfiniteAnchor direction="up" />
    <DataGrid columns={columns} />
    <DataGridInfiniteAnchor direction="down" />
  </DataGridProvider>
</DataGridUIProvider>

That's it. Don't render <DataGridPagination> — there's no "page N" to step through.

How it works

Three pieces — one provider mode, one hook, one UI primitive.

  1. <DataGridProvider paginationMode="infinite"> — overrides refresh() to always fetch the first cursor page on filter / sort / search change. Tracks topCursor + bottomCursor and exposes a loadMore(direction) method on the context.
  1. useDataGridInfiniteScrollSentinel({ enabled, onTrigger, rootRef?, rootMargin? }) — pure IntersectionObserver wrapper. Returns a ref you attach to any element. Fires onTrigger whenever the element enters the root's intersection rectangle.
  1. <DataGridInfiniteAnchor direction="up | down" /> — drop-in component combining the two. Reads useDataGrid().infinite.hasMore[direction] to decide whether to attach the observer. Renders a small "Loading more…" spinner while a page is in flight; renders "End of list" once hasMore[direction] flips false.

Bidirectional

Both direction="up" and direction="down" are supported. In a typical "land on page 1 and scroll forward" flow, only the down anchor ever fires — hasPreviousPage starts false because nothing has been loaded before the first cursor.

The up direction matters when you deep-link into the middle of a list (e.g. /users?cursor=u_500 lands on user 500 mid-feed). The first load returns rows centered on that cursor and the adapter sets hasPreviousPage: true. Scrolling up fires the up sentinel; the provider issues a backward cursor query ({ last: pageSize, before: topCursor }) and prepends the result.

The provider exposes both edges separately so each direction loads independently — no coupling between up + down loads.

Infinite scroll vs. windowing (virt rows)

These two are constantly confused — they solve different problems and stack cleanly.

Windowing (also called virtualization or virt rows) is the technique of rendering only the rows currently visible in the viewport — the "window" — and recycling DOM nodes as the user scrolls. It controls how many of the already-loaded rows are rendered to the DOM. In this kit, windowing ships as <DataGridVirtual> (powered by @tanstack/react-virtual).

Infinite scroll controls how many rows get fetched from the server. It appends new cursor pages into the JS rows array as the user scrolls past a sentinel.

Concrete pairings:

  • Windowing only — adapter returns 5000 rows in one load(). JS array has 5000. DOM has ~30. Scrolling = DOM recycle. Network = one fat request.
  • Infinite only — adapter returns 30 per page. JS array grows: 30 → 60 → 90 → … DOM = JS array length. Scrolling = fire next fetch. Network = many small requests.
  • Both — adapter returns 30 per page. JS array grows: 30 → 60 → … DOM stays ~30 regardless. Scrolling does both: triggers the window shift AND triggers the next-page fetch when the sentinel hits.

When to use which

  • Server-side dataset is big (10k+ rows, paginated API) → infinite (or just classic <DataGridPagination>).
  • All rows already in the client array (5k rows from one load(), 50k in a CSV import preview) → windowing.
  • Both big (cursor-paginated feed AND each page is 500 rows) → stack both.
  • Small list (< 200 rows total) → neither, just paged or unpaginated.

That's why the kit puts infinite at the provider layer (data) and windowing at the layout layer (render). No overlap, no duplication, and you turn each one on independently.

Plain-language version (no jargon)

Pretend the dataset is a library and the user is a reader.

  • Windowing is having only the books currently open on the table visible. The shelves still hold all the books — you just don't put every one of them on the table at once. The table is the DOM; the shelves are the JS rows array. Fixes "the table is too cluttered" (DOM bloat → slow scroll).
  • Infinite scroll is fetching new books from the warehouse to the shelves as the reader asks for more. The shelves don't start full — they grow over time. Fixes "the truck from the warehouse is too big" (one giant load() → slow first paint, big payload, big memory).

So:

  • Reading 5k books from a stocked library? Windowing only.
  • Reading from a 500k-book warehouse? Infinite scroll only — or you'll never get the first page rendered.
  • Both? Stack them. Infinite keeps trucks small; windowing keeps the table tidy.

Why each alone has a ceiling

Approach aloneWhere it breaks
Windowing onlyFirst load() still has to return all rows. Backend has to return everything (no LIMIT). 5k = fine, 50k = painful, 500k = the tab freezes for 10s on first paint.
Infinite onlyAfter 100 cursor pages of 30 rows each, the array has 3000 rows and the DOM has 3000 <tr>s. Scroll FPS tanks even though network was fine.
BothNetwork: one small page at a time. DOM: one window at a time. Scales to millions.

Composing windowing with infinite

Windowing and infinite scroll are orthogonal concerns. The infinite-scroll primitive lives at the provider layer; the windowing primitive (<DataGridVirtual>) lives at the layout layer. They compose without duplication:

<DataGridProvider paginationMode="infinite">
  <DataGridInfiniteAnchor direction="up" />
  {/* DataGridVirtual reads rows from the same provider — as more pages
      append, the virtualizer's range simply grows. */}
  <DataGridVirtual columns={columns} />
  <DataGridInfiniteAnchor direction="down" />
</DataGridProvider>

The sentinel still needs to be in the DOM to fire. If the windowed scroll happens inside a fixed-height pane, place the down anchor inside that container's footer slot (or pass rootRef to scope the observer to that pane).

Full combo example — 500k-row feed

The shape that scales to millions. Network stays small (30 rows per cursor page), DOM stays small (~30 rendered), filter / sort / selection all keep working because the provider doesn't care which layout is rendering.

import {
  DataGrid,                       // (or DataGridVirtual — same data, different renderer)
  DataGridVirtual,
  DataGridFilterBar,
  DataGridInfiniteAnchor,
  DataGridProvider,
  DataGridUIProvider,
  createInMemoryAdapter,
  defineColumns,
} from '@kitora/datagrid'

const columns = defineColumns<User>()([
  { id: 'name',  header: 'Name',  cell: (r) => r.name },
  { id: 'email', header: 'Email', cell: (r) => r.email },
  { id: 'team',  header: 'Team',  cell: (r) => r.team },
])

export function MillionRowFeed({ adapter }) {
  return (
    <DataGridUIProvider defaultPageSize={30}>
      {/* paginationMode="infinite" → cursor pages append; classic
          <DataGridPagination> is not rendered. */}
      <DataGridProvider adapter={adapter} paginationMode="infinite">
        <DataGridFilterBar />

        {/* (Optional) load the previous page if user lands mid-feed. */}
        <DataGridInfiniteAnchor direction="up" />

        {/* Windowing — only ~30 rows mounted at a time regardless of
            how many cursor pages the provider has appended. */}
        <DataGridVirtual columns={columns} estimateRowHeight={44} />

        {/* Sentinel below the windowed list — fires loadMore('down'). */}
        <DataGridInfiniteAnchor direction="down" />
      </DataGridProvider>
    </DataGridUIProvider>
  )
}

What happens at runtime:

  1. First mount → adapter returns 30 rows. Virt renders the ~30 that fit on screen.
  2. User scrolls down → virt recycles DOM nodes inside the existing window. Eventually the bottom sentinel enters the viewport.
  3. Sentinel fires → provider calls adapter.load({ first: 30, after: bottomCursor }) → appends 30 more rows.
  4. Virt's range expands automatically; still only ~30 in DOM. Sentinel moves further down.
  5. User keeps scrolling → repeat.

At 500k rows total, the JS array eventually holds whatever portion the user scrolled to (say 1k–5k); the DOM stays at ~30. Network is ~17 small requests for the first 500 rows, none of them blocking the first paint.

Tips:

  • Pick defaultPageSize to slightly exceed one viewport's worth of rows. Too small → constant network chatter. Too big → wasted bytes for users who only scroll one page.
  • If the virt scroller sits inside a fixed-height pane (not the body), pass rootRef to <DataGridInfiniteAnchor> so the IntersectionObserver scopes to that container.
  • Selection / filters / sort all keep working unchanged — neither windowing nor infinite scroll touches that state.

Customizing the anchor

Replace the spinner / end-state via children:

<DataGridInfiniteAnchor
  direction="down"
  endSlot={<span>You've reached the end of the feed.</span>}
>
  <MyCustomSpinner />
</DataGridInfiniteAnchor>

Or skip <DataGridInfiniteAnchor> entirely and call the hook directly to build a "Load more" button:

function LoadMoreButton() {
  const { infinite, paginationMode } = useDataGrid()
  if (paginationMode !== 'infinite' || !infinite.hasMore.down) return null
  return (
    <button onClick={() => infinite.loadMore('down')}>
      {infinite.loadingMore.down ? 'Loading…' : 'Load more'}
    </button>
  )
}

Adapter contract

No new adapter surface. Infinite scroll uses the same first / after / last / before cursor inputs and the same pageInfo: { hasNextPage, endCursor, hasPreviousPage, startCursor } outputs that <DataGridPagination> already uses. If your adapter supports cursor pagination, infinite mode works.

The provider dedupes rows by getRowId on every append — overlapping pages won't double-render.
