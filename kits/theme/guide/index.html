How design languages work

Tokens, component style slots and layout presets: how a language reaches the page, how to make your own, and how a component joins in.

Three layers

A design language decides how the whole UI looks, not only its colours. It has three layers, and each one can be switched live.

LayerWhat it holdsExample
TokensThe colours and the font family. source: "host" keeps the page's own tokens; source: "generated" builds a contrast-checked theme from a seed with buildTheme.Material 3 generates a purple theme; Kitora and macOS keep the page's.
SlotsHow each component is shaped: one slot per component (button, input, select, dialog, table, motion and 25 more). A slot is a few typed fields: sizes, corners, fills per light and dark, and small enums such as elevation or focusRing.macOS buttons get a sheen and a raised edge; Retro gets a bevel and square corners.
LayoutA preset for the app frame: window chrome, where the toolbar goes, where the header sits, the sidebar's surface and active row, and a dock or a taskbar.macOS merges the toolbar into the title bar and keeps a dock.

A language is plain data: the DesignLanguage type in @kitora/theme/core. It holds no CSS, no Tailwind classes and no React, and a test keeps it that way. That is why the same language can later drive another renderer.

How a language reaches the page

  1. 1. Language data
    @kitora/theme/core
    slots.button.corner = { px: 999 }
  2. 2. DOM adapter
    @kitora/theme/dom
    slotDeclarations → --dk-button-radius: 999px
  3. 3. One stylesheet
    data-language + boundaries
    [data-language="pill"] { --dk-button-radius: … }
  4. 4. Component
    @kitora/ui
    rounded-[var(--dk-button-radius, …)]
  1. Data. A DesignLanguage names a token, a corner or an enum value, never a CSS value. A colour is always a token reference such as { token: "primary", alpha: 0.3 }.
  2. DOM adapter. languageCss(languages) in @kitora/theme/dom turns every registered language into one stylesheet. slotDeclarations(language, scheme) maps each slot field to a variable named --dk-<slot>-<field>, for example --dk-button-radius or --dk-input-h. Enums become CSS here: fill: "gradient" becomes a gradient, surface: "translucent" a blur.
  3. Attribute. Each block is keyed by data-language="<id>". Switching language only changes that attribute, so nothing re-renders. The variables are declared again at every LANGUAGE_BOUNDARY (.dark, .light and [data-theme-scope]), so a dark island or a ThemeScope resolves them against its own tokens.
  4. Components. Every styled component in @kitora/ui reads the variables with its old look as the fallback:
// packages/ui/src/badge.tsx (shortened)
"h-[var(--dk-badge-h,calc(var(--spacing)*5))] rounded-[var(--dk-badge-radius,calc(var(--radius)*2.6))]"

With no language on the page, every var() falls back, so Kitora looks exactly as it always did. The kitora language writes those same fallback values.

Providers and scopes

APIUse it for
LanguageProviderThe language for a whole app (target="root", sets data-language on <html>) or for a wrapper (target="scope"). It remembers the choice in localStorage; pass storage={null} to keep nothing. ThemeProvider takes the same language props when it also owns light and dark.
LanguageScopeOne subtree in another language, beside the page's own. It takes an id or a whole DesignLanguage.
useLanguage()The active language, setLanguage(id) and the list on offer, for a picker.
useLayout()The active language's layout preset.
languageBootScript(key)A tiny <head> script that sets data-language before first paint, so a reload does not flash the default.

Popups keep the language of the scope they open from. Anchored popups (menus, popovers, tooltips, selects, comboboxes) portal into a host at the end of the scope. Fixed popups (dialogs, sheets, drawers) stay in the body and carry the scope's data-language on their portal node. No container prop is needed.

Built-in languages and the registry

Seven languages ship: kitora (the default), macos, windows, material, gnome, retro and terminal. They are listed in BUILTIN_LANGUAGES.

A registry is the list a provider offers. builtinLanguageRegistry() returns a fresh one holding the built-ins, with Kitora as the default. register(language) adds yours and throws with every problem listed if it is not valid. resolve(id) falls back to the default for a missing or unknown id, so a stale stored choice never breaks the page. A provider reads a registry once, so register your languages before you pass it in.

Make your own language

Start from a built-in and change only the fields you care about, then register it.

const PILL: DesignLanguage = {
  ...KITORA_LANGUAGE,
  id: "pill",
  label: "Pill",
  slots: {
    ...KITORA_LANGUAGE.slots,
    button: { ...KITORA_LANGUAGE.slots.button, corner: { px: 999 } },
  },
}
const registry = builtinLanguageRegistry()
registry.register(PILL)
// <LanguageProvider languages={registry}> … </LanguageProvider>

Put a component on a slot

There are two cases.

Your own component. Read the variables of an existing slot, each with your current value as the fallback. Use Tailwind's type hints (length:, weight:, color:, shadow:) so Tailwind and tailwind-merge know what the variable holds.

A new slot in @kitora/theme. This is how every @kitora/ui component was converted:

  1. Add a slot interface (FooSlot) in packages/theme/src/core/language.ts, add it to LanguageSlots and SLOT_IDS, and give each field a check in SLOT_SCHEMA. The schema drives validateLanguage and the customizer's controls.
  2. Map each field to a variable in slotDeclarations in packages/theme/src/dom/language.ts. Turn enums into CSS here. A field that differs between light and dark is a PerScheme value.
  3. In the component, swap each class for var(--dk-foo-<field>, <old value>), keeping the exact old value as the fallback. A value that differs per variant needs its own variable.
  4. Add the file to CONVERTED in packages/theme/src/__tests__/language.test.ts. The tests then check that every variable the component reads is written by every language, and that no written variable is dead.
  5. Fill the slot in every built-in in packages/theme/src/core/languages.ts, with Kitora's values equal to the old classes.
  6. Add a contrast guard for any new text or state colour: 4.5:1 for text and 3:1 for the edge or fill that shows a state. Break it once on purpose to see it fail.
  7. Prove Kitora is pixel-identical: before and after screenshots of each page that renders the component, at 390 and 1280 px, light and dark.

Code colours: the code slot

The code slot colours highlighted code everywhere: the display kit's code blocks, the editors' read-only code, markdown preview and rich-text code blocks, ai-chat's code blocks, and the editors' CodeMirror editor, so an editor and a read-only block look the same. Its palette is kit (Kitora's own colours, written as initial) or one after a platform's editor (github, xcode, vscode, material, adwaita, retro, terminal), and comments is italic or normal. Each token kind becomes a variable, --dk-code-keyword, --dk-code-string and so on; the display kit's TOKEN_CLASS reads them with Kitora's colours as fallbacks. The languages page shows a code block in every built-in.

Each built-in's choice is plain data you can read (hover or focus a name for its type; this block is type-checked at build time):

import { BUILTIN_LANGUAGES } from "@kitora/theme/core"

const palettes = BUILTIN_LANGUAGES.map((language) => language.slots.code.palette)

Parts without a slot of their own: base, list, chip and bubble

Most kit parts (panels, frames, windows, the gallery's own boxes) have no slot. Four slots reach them anyway:

  • base works through the page's scales rather than per component. radius sets the base radius every rounded-* class is a multiple of, written as --radius from the page's own (captured as --dk-host-radius, so a theme lab's radius still scales). shadows swaps Tailwind's whole shadow scale, which src/styles.css routes through --dk-base-shadow-<step> with its own values as fallbacks. Retro and Terminal square every corner on the site this way; Retro's panels bevel. It also holds the two shared corners: control (every input-like control and button, at every size) and surface (cards, popovers, menus, dialogs). A slot's corner names one with { role: "control" } or { role: "surface" }; Kitora's controls and surfaces all do, so changing base.control rounds every input, select, button and toggle at once and two controls of one height can never disagree.

  • list styles rows that are not menus: the collections tree, task rows, the tabster outliner, the inbox and the gallery's navigation. It sets the corner, the selected row (tint, neutral, solid for a macOS source list or Retro's navy bar, inverse for Terminal) and the hover.

  • chip styles tags, status pills, filter chips and key caps: a pill or square shape, flat, raised or bevel keys, and ink text on tinted pills.

  • bubble styles message bubbles (ui's Bubble, which the ai-chat and chat kits draw their messages through): a round or square shape, the tail (none, or soft at half the corner) and the fill of one's own bubble (primary, tinted or muted). macOS and GNOME draw round bubbles with one's own in the primary colour, Windows 11 and Material keep the base corner with a tinted own bubble, Retro and Terminal square them.

kit is a value only Kitora uses: each part keeps its own look. Kitora's rows and chips differ from part to part (a tree selects with a 10% brand tint and 5px corners, a task row with 8% and none), so one shared Kitora value would change some of them. With kit the adapter writes initial, and each part falls back to its own old class.

Checking every language

  • A test reads languages.ts and fails when a built-in leaves a slot out of its own literal (a spread from another language) or names no layout preset.
  • task languages:smoke -- <url> [--shots dir] opens a fixed set of pages in every built-in language, light and dark. It checks that the language is applied, that there are no console errors, and that axe reports 0 serious or critical issues and the page does not scroll sideways at 1280 px. At 390 px it checks for sideways scroll. Run it after any change to a slot, a language or a shared layout.

Layout presets

A language names its preset by id in layout. layoutFor(language) in core, or useLayout() in React, returns the preset, and kitora is the fallback for an unknown id.

FieldValuesPassed to
windowChromeneutral, mac, windows, material, gnome, retro, terminalwindows kit: createChrome(windowChrome, …)
toolbarbelow-title, in-titlewindows kit: createChrome(…, { toolbar })
headerPlacementcontent, fullshell: AppShell headerPlacement
sidebarSurfacesolid, translucentshell: AppShell sidebarSurface
activeRowbar, fill, pillshell: AppShell sidebarActiveRow
appSwitchernone, dock, taskbarwindows kit: render DesktopDock or Taskbar
navigationsidebar, railshell: start the sidebar collapsed to its icon rail (Material's navigation rail)
statusBarnone, lineshell: AppShell footer={<ShellStatusBar … />} (Retro, Terminal)
headerTitlestart, centershell: ShellHeader with its title centred (a GNOME header bar)

Every built-in language names its own preset: kitora, macos-titlebar, windows-titlebar, material-appbar, gnome-headerbar, retro-titlebar and terminal-statusline. The gallery itself follows the preset: its navigation rows read the list slot, a statusBar: "line" preset adds a status line along the bottom of the window, and the windows kit's desktop demo starts in the language's chrome.

The windows, shell and sidebar kits never import the theme kit. The app reads the preset and passes each value on:

const layout = useLayout()
const chrome = useMemo(() => createChrome(layout.windowChrome, { toolbar: layout.toolbar }), [layout])
// <AppShell headerPlacement={layout.headerPlacement} sidebarSurface={layout.sidebarSurface} sidebarActiveRow={layout.activeRow} … />
// {layout.appSwitcher === "taskbar" ? <Taskbar /> : null}

The "One app, every layout" demo on Design languages does exactly this in every built-in.
